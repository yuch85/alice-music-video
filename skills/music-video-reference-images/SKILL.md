# Keyframe Generation & Approval Skill (Stage 6)

Generates shot-specific keyframe candidates for each shot using QEI (Qwen Image Edit)
based on the storyboard's visual weight. The user approves one keyframe per shot
before the workflow proceeds to prompt generation.

## Image Generation Workflow (Keyframe Pipeline)

The proven production workflow for music video image generation:

```
Canonical portraits (persistent assets)
  |
  +-> QEI keyframe generation
  |   (composition, framing, pose, camera angle,
  |    weather, wardrobe, environment, lighting)
  |   |
  |   v
  |  Shot-specific keyframe candidate
  |   |
  |   v
  |  Human QC
  |  (identity, continuity, framing, composition,
  |   wardrobe, weather, lighting, emotion)
  |   |
  |   v
  |  Approved keyframe (first frame of shot)
  |   |
  |   v
  |  LTX animation
  |  (temporal animation, camera movement,
  |   facial motion, body motion, environmental motion)
  |   |
  |   v
  |  Editing & final assembly
```

## Tool Responsibilities

| Tool | Responsible For | NOT Responsible For |
|------|----------------|---------------------|
| **QEI** | Composition, framing, pose, camera angle, weather, wardrobe state, environment, lighting | Temporal animation, motion |
| **Human QC** | Identity verification, continuity, emotional correctness, cinematic quality | Generation decisions |
| **LTX** | Temporal animation, camera movement, facial motion, body motion, environmental motion | Shot design, framing, composition |

**Critical**: LTX should NOT be relied upon to invent framing or redesign shots. The keyframe (produced by QEI and approved by Human QC) determines composition. LTX only adds temporal motion to the approved keyframe. See the ref-image dominance principle in the `ltx-prompting` skill: I2V first-frame composition inherits from the keyframe more strongly than prompt text can override it.

## Terminology

| Term | Definition |
|------|-----------|
| **Canonical portrait** | Permanent character reference image. One per character. Never changes. |
| **Shot-specific keyframe** | Per-shot first frame generated by QEI from the canonical portrait, tailored to the shot's framing, lighting, and continuity requirements. |
| **Approved keyframe** | A shot-specific keyframe that has passed Human QC (identity, continuity, framing, composition, wardrobe, weather, lighting, emotion). Only approved keyframes proceed to LTX. |
| **Continuity-state variant** | Persistent asset for character state changes (e.g., wet-state for rain scenes). Pre-approved to ensure consistency across all shots in that state. |
| **Persistent asset** | Assets that survive beyond a single shot: canonical portraits and continuity-state variants only. |

## Persistent Assets Philosophy

Persistent assets are limited to:
1. **Canonical character portraits** — one per character, locked after approval.
2. **Continuity-state variants** — additional persistent assets where continuity genuinely benefits (e.g., wet-state variants for rain scenes).

Everything else is generated per-shot. Shot-specific keyframes are NOT permanent assets — they are generated on demand via QEI and used for their specific shot. Do not build large reference libraries.

## Input

Read ALL of these files from the project directory:

2. `storyboard.md` — visual weight, narrative importance, rationale, viewer focus

## Process

### Step 1: Determine Candidate Counts

For each beat in the shot list, look up its storyboard entry to get `visual_weight`.
Map visual weight to candidate count:

| Visual Weight | Candidates | Beat Type |
|---------------|-----------|-----------|
| 1-3 | 2-3 | Transitional / filler beats |
| 4-6 | 3-4 | Supporting performance beats |
| 7-10 | 5-8 | Hero moments / emotional peaks |

### Step 2: Canvas-Expand Source Images to 16:9

Qwen Image Edit (QEI) inherits the output dimensions from the input reference image. Source portraits are typically portrait-oriented (e.g., 944x1104), but LTX video generation outputs at 16:9 landscape 1080p (1920x1088 via the combined two-stage workflow).

**Why 1088, not 1080?** LTX-2 base height must be divisible by 32 (VAE spatial downsample), so base_h = 544 (= 17×32). The 2x upscale yields 1088 (= 2×544). Final output is cropped to 1920×1080 in post-production. If a portrait-oriented keyframe is fed into LTX, the model must invent left/right content, causing compositional artifacts.

**Before sending any reference image to QEI, canvas-expand it to 16:9:**

```bash
# Expand portrait to 16:9 with blurred background (target: 1024x576)
ffmpeg -i input.jpg -filter_complex \
  "[0:v]scale=1024:576:force_original_aspect_ratio=increase,pad=1024:576:(ow-iw)/2:(oh-ih)/2,color=black[bg]; \
   [bg]blur=50[blurred];[blurred]format=rgb24" \
  -y output_169.jpg
```

Target resolution: 1024x576 (or any 16:9 resolution matching the project's target). The blur-expand fills the empty canvas areas with a blurred version of the image, giving QEI a natural-looking background rather than hard black bars.

Apply this to ALL source images: canonical portraits and continuity-state variants. Store expanded versions alongside originals (e.g., `portrait_169.jpg`).

### Step 3: Identify Source Portrait Per Shot

For each shot, determine which canonical portrait or continuity-state variant to use as the QEI source (use the 16:9 canvas-expanded version):

- **Character shots:** Use the 16:9 canvas-expanded canonical portrait (or continuity-state variant). QEI generates the shot-specific keyframe from this source, tailored to the shot's framing, lighting, and environment.
- **Two-character shots:** QEI generates the complete two-character keyframe from both 16:9 canvas-expanded canonical portraits. QEI handles all composition, framing, and relative positioning of both characters. Human approves the keyframe. LTX animates from the approved keyframe. LTX is NOT responsible for compositing multiple characters.
- **Environment-only shots:** No character reference needed. LTX prompt + environment description is sufficient.

**Identity lock rule:** The canonical portrait MUST be a real photo. AI-generated portraits drift from canonical identity. QEI generates shot-specific keyframes FROM the real portrait — the portrait itself is never AI-generated.

### Step 4: Validate Wardrobe Lock

Before generating ANY images, verify the continuity bible has a **specific, unambiguous wardrobe definition** (exact color, garment type). If the wardrobe is vague ("earth tones", "natural colors", "understated outfit") — STOP and ask the user to specify the exact wardrobe before proceeding. Vague wardrobe definitions cause inconsistent outputs across generations.

### Step 5: Build QEI Prompts

For each shot, construct a QEI prompt incorporating:

- **Shot type, angle, composition** from shot list (e.g., "close-up, face filling the frame")
- **Character description, wardrobe** from continuity bible — include the EXACT wardrobe color and garment type (e.g., "wearing a white top and dark trousers", not "earth-toned clothing")
- **Environment, lighting, mood** from continuity bible + treatment
- **Shot-specific narrative context** from storyboard rationale
- **Primary viewer focus** from storyboard (e.g., if focus is "eyes", ensure eye detail is prominent)

**CRITICAL:** The wardrobe string must appear explicitly in EVERY prompt. Do not rely on the reference image alone to maintain wardrobe consistency — the I2I model will drift if the prompt doesn't reinforce it.

**16:9 framing:** Always include 16:9 landscape framing cues in the prompt (e.g., "landscape composition", "wide framing") to reinforce the canvas-expanded input. QEI can still produce portrait-biased composition even with a 16:9 input if the prompt doesn't guide it.

### Step 6: Generate Keyframe Candidates

Use `alice_image_to_image` MCP tool (QEI) to generate keyframe candidates:

- **Model:** `qwen-gguf-q3` (9GB VRAM, default for keyframe variants)
- **Steps:** 20 for production keyframes (quality path, cfg=4.0)
- **Input:** Feed the canonical portrait (or continuity-state variant) for best identity lock
- **Cropping:** For closeup shots, use head-and-shoulders crops (~1:1 or 3:4 aspect). For zoom variants, use top-biased crops.

Store each candidate in `approvals/Beat_<ID>/candidate_<a/b/c/d/etc>.png`.
All candidate images use `.png` extension consistently.

### Step 7: History Principle

When regenerating keyframe candidates for a shot (user rejects all and requests new ones),
write new candidates with incremented labels so no historical attempts are overwritten:

- First generation: `candidate_a.png`, `candidate_b.png`, `candidate_c.png`
- Regeneration: `candidate_a_v2.png`, `candidate_b_v2.png`, `candidate_c_v2.png`

Every generation attempt is preserved for post-hoc inspection.

### Step 8: Present Keyframe Candidates for Approval

Display all candidates to the user. Wait for approval of one keyframe per shot.

### Approved Keyframe QC Criteria

Before marking a keyframe as approved, verify:

| Check | Criteria |
|-------|----------|
| **Face identity** | Must match canonical portrait. Same facial structure, features, expression style. |
| **Clothing continuity** | Must match Continuity Bible exactly. No added accessories, no color shifts. |
| **Framing** | Must match shot list framing (XW/Wide/Full/Med/MCU/CU/ECU). |
| **Lighting** | Must match storyboard lighting state for the segment. |
| **Weather state** | Dry shots must show dry clothing/hair. Wet shots must match wet-state variant level. |
| **Props** | All props from Continuity Bible must be present where specified. No extraneous props. |
| **Emotion** | Must match the beat's emotional purpose from the storyboard. |

Common rejection reasons from production experience:
- Repetitive settings (e.g., lake shot following a lake shot)
- Wrong props (e.g., guitar when character should not have one)
- Unnatural objects (e.g., microphone appearing from water)
- Static scenes without camera motion potential

### Step 9: Generate HTML Approval Dashboard

After all keyframe candidates are generated for all shots, write `approval_dashboard.html`
in the project directory. The dashboard is a self-contained HTML file (inline CSS
and JS, no external dependencies).

**Dashboard renders per-beat sections containing:**

- **Beat Metadata:** Timing (start-end), visual weight, lyrics, shot scale, camera movement intensity (from storyboard.md)
- **Candidate Images:** Display all candidates side-by-side with labels (candidate_a, candidate_b, etc.) using relative paths (`approvals/Beat_{ID}/candidate_{X}.png`)
- **Prompt Text Fields:** Editable text fields for Keyframe Prompt, Motion Prompt, Camera Prompt, and Negative Prompt. In Stage 6 these show placeholder text ("prompts will be generated in Stage 7"). In Stage 7 (after prompt generation), the dashboard can be regenerated with pre-populated prompts for user review and editing.
- **Selection Controls:** Radio buttons for candidate selection (one approved candidate per beat)
- **"Generate Reply to Agent" button:** JavaScript `compileReply()` function that:
  - Reads all selections and text field values
  - Constructs a JSON array:
    ```json
    [
      { "beat": "B01", "approved_candidate": "a", "revised_keyframe_prompt": "...", "revised_motion_prompt": "...", "revised_camera_prompt": "..." },
      { "beat": "B02", "approved_candidate": "c", "revised_keyframe_prompt": "...", "revised_motion_prompt": "...", "revised_camera_prompt": "..." }
    ]
    ```
  - Displays the JSON in a `<pre><code>` block for easy copy-pasting

Write the HTML file using the `Write` tool.

### Step 10: Record Approvals

On approval, record the approved keyframe path in `refs/manifest.json`. The manifest maps beat index to approved keyframe path in `approvals/`. Include `visual_weight` from storyboard for downstream reference.

The `refs/` directory contains:
- `refs/portrait.jpg` — the canonical portrait
- Approved final keyframes (symlinked or copied from `approvals/`)

There is no legacy `refs/beat_{NN}/` candidate path — candidates live exclusively in `approvals/`.

### Step 11: Track Progress

Track approval status per beat in `index.md`.

## Resumability

If `refs/manifest.json` exists with approved entries, skip already-approved shots.
Only generate keyframe candidates for pending shots.

## QEI Configuration

| Parameter | Value | Notes |
|-----------|-------|-------|
| Model | `qwen-gguf-q3` | 9GB VRAM, default for keyframe variants |
| Steps | 20 | Quality path (cfg=4.0) for production |
| Steps (preview) | 4 | Lightning fast (cfg=1.0) for iteration |
| Input | 16:9 canvas-expanded portrait | Must be 16:9 — QEI inherits input dimensions |
| Closeup shots | QEI handles framing via prompt | Do NOT pre-crop; let QEI compose within 16:9 canvas |
| Zoom variants | Top-biased composition in prompt | Face in upper portion, described in prompt |

## Critical Rules

1. **All QEI output must be 16:9 landscape.** QEI inherits dimensions from the input image. Source portraits are typically portrait-oriented; they MUST be canvas-expanded to 16:9 (e.g., 1024x576) before sending to QEI. LTX video outputs at 16:9 — portrait keyframes cause LTX to invent left/right content, producing compositional artifacts. See Step 2 for the canvas-expand recipe.
2. **Canonical portraits must be real photos.** AI-generated portraits drift from canonical identity. Only a real photo produces correct facial identity. QEI generates shot-specific keyframes FROM the real portrait — the portrait itself is never AI-generated.
3. **QEI generates keyframes, not identity.** QEI's job is to adapt the canonical portrait to each shot's framing, lighting, environment, and continuity state. It does not create new identities.
4. **Environment-only shots need no character keyframe.** Landscape, atmospheric, and empty-environment shots use LTX prompts + environment description without character reference images.
5. **All GPU operations go through slingshot.** QEI image generation uses `alice_image_to_image` MCP which internally routes through the GPU via slingshot.

- `approvals/Beat_<ID>/` directories with keyframe candidate images (`.png` extension)
- `refs/manifest.json` — maps beat index to approved keyframe path in `approvals/`, includes `visual_weight`
- `refs/portrait.jpg` — canonical portrait (copied from project if not present)
- `approval_dashboard.html` — self-contained HTML approval dashboard
- `index.md` — updated with approval status per shot
